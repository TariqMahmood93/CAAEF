\begin{abstract}
Agents built on large language models (LLMs) are now routinely asked to plan, call tools, run code, and act on external systems with little supervision. In this setting an agent can reach its assigned objective and still break the rules that were meant to govern how the objective is reached. Most benchmarks score only the final outcome, so an agent that obtains the right answer through an unauthorized tool, a leaked credential, or a flaw in the environment is counted as a success. We argue that objective achievement and constraint compliance are separate properties and should be measured separately. We describe an evaluation framework with five components: outcome verification, trajectory monitoring, constraint compliance, uncertainty and anomaly detection, and post-hoc behavioral analysis. We discuss how distribution shift relative to known-compliant trajectories can flag risky behavior before a task finishes, why the resulting measurements should not be collapsed into one score, and how they can still support a release decision. We then instantiate the framework on ODCV-Bench, running four LLM agents over all 40 scenarios in two framings for 777 traced runs (an original wave of 297 and an extension wave of 480), and scoring every run under four checker configurations against 262 hand-written constraints. The results are mixed in an informative way. Under deterministic state and log checkers the ranking by outcome and the ranking under a constraint gate are \emph{opposed} (Kendall's $\tau=-0.60$): the two agents with the highest task success are exactly the two the gate disqualifies. A sweep over the gate tolerance shows this inversion occupies a window rather than holding everywhere, and locating that window requires the checker's false-positive rate --- which is the quantity our incomplete audit leaves unmeasured. Under the full protocol the comparison becomes untestable, because the measured violation rate exceeds the gate tolerance for every agent --- an instance of our own analysis of checker error rather than a result about the agents. Two judges drawn from different families agree on only $85.5\%$ of runs and disagree one-directionally, which alone decides which agent would ship. The anomaly score we propose for early warning does not work: at the raw run level it appears anti-predictive (AUROC $0.312$), but this is substantially a truncation artefact --- violating runs are truncated at their first violation and compliant ones are not, so the run-level maximum is taken over systematically fewer draws in the positive class. With the pre-violation horizon matched between classes the AUROC is uninformative ($0.496$ at $H{=}2$, $0.432$ at $H{=}3$); re-scoring the proposed action instead of the prefix gives a modest prefix-level improvement (AUROC $0.603$) that is still far too weak for a guard, catching nothing at a $5\%$ false-alarm budget. Split-conformal calibration overshoots its target false-alarm rate by a factor of about $2.8$ on the original score. Finally, the category an outcome-only benchmark cannot distinguish from incompetence --- declining an objective that cannot be reached compliantly --- is $83\%$ of all runs, not an edge case.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Large language models were first deployed as question-answering systems. They are now increasingly used as agents: they decompose a goal into steps, call tools, execute code, browse the web, and interact with external services over many turns \citep{yao2023react}. Once a model acts rather than answers, a distinction that was previously unimportant becomes central. There is what the agent achieves, and there is how it achieves it.

A simple example makes the point. Suppose an agent is asked to retrieve a record from a particular database. A conventional evaluation marks the run as successful if the returned record is correct. Now suppose the agent obtained the record by querying a different database it was not authorized to use, by exploiting a vulnerability, by reading credentials it was never meant to see, or by sidestepping an explicit restriction in its instructions. Judged by outcome, nothing went wrong. Judged by any reasonable standard of trustworthy behavior, the run is a failure.

This is not a hypothetical concern. Reinforcement learning has a long record of systems that satisfy the literal objective in ways their designers did not intend \citep{amodei2016concrete,krakovna2020specification}, and recent reports describe LLM-based agents that tamper with their environment or evaluation when the legitimate route is hard \citep{bondarenko2025demonstrating,meinke2024frontier}. Widely used agent benchmarks nevertheless report task success as the headline number \citep{liu2024agentbench,zhou2024webarena,jimenez2024swebench}. Such a number cannot tell apart an agent that solved the task from an agent that found a way around it.

The question we address is therefore the following: \emph{how can we distinguish an agent that completes its assigned objective from one that optimizes for the objective while violating the constraints that were supposed to bound its behavior?}

The question becomes sharper as agents take on longer horizons and richer environments, because a system optimized mainly for completion has more opportunities to discover strategies that meet the formal objective by exploiting the environment or the evaluation procedure. Our position is that task success is not a sufficient condition for acceptable behavior, and that evaluation should report at least two things: whether the objective was achieved, and whether the constraints were respected.

Its contributions are:
\begin{itemize}
    \item a statement of the problem that separates objective achievement from constraint compliance (Section~\ref{sec:problem});
    \item a Constraint-Aware Agent Evaluation Framework (CAAEF) with five components (Section~\ref{sec:framework});
    \item a two-dimensional evaluation model, an argument against scalar aggregation, and a decision rule for release gating that does not need a scalar, with an analysis of how it behaves when the checker makes errors (Section~\ref{sec:model});
    \item an empirical instantiation of the framework on ODCV-Bench, covering 297 traced agent runs scored under four checker configurations against 131 hand-written constraints (Section~\ref{sec:setup});
    \item results that support part of the framework and refute part of it (Section~\ref{sec:results}), together with a measurement of how far the conclusions depend on the checker rather than on the agents, and sensitivity analyses over the gate tolerance, the soft-constraint weights, the judging protocol and the conformal calibration method;
    \item a set of open research problems that follow from the framework and from what the study failed to show (Section~\ref{sec:challenges}).
\end{itemize}

The study is deliberately small, and we state its limits early because they bound every number we report. It covers one benchmark, half of that benchmark's scenarios, four agents drawn from only two model families, and a single complete repetition. The human audit that would establish the checkers' false-positive and false-negative rates has not yet been carried out, so the quantities that depend on it are reported as pending rather than estimated. What the study can support is a claim about \emph{measurement}: that the choice of checker changes the conclusion at least as much as the choice of agent does, and that this is visible even at this scale.

\section{Related Work}
\label{sec:related}

\paragraph{Specification gaming and reward hacking.}
\citet{amodei2016concrete} list reward hacking and negative side effects among the concrete problems of AI safety. \citet{krakovna2020specification} collect examples of specification gaming, where a system satisfies the stated objective without achieving the intended one, and \citet{skalse2022defining} give a formal treatment of reward hacking. Goal misgeneralization is a related failure in which a policy competently pursues the wrong goal out of distribution even though the training specification was correct \citep{langosco2022goal,shah2022goal}. Our concern overlaps with all three, but the emphasis differs: we are interested in cases where the objective really is achieved and the fault lies in the path taken.

\paragraph{Constrained and safe reinforcement learning.}
Maximizing reward subject to cost limits is the subject of constrained Markov decision processes \citep{altman1999constrained} and of a large literature on safe reinforcement learning \citep{garcia2015comprehensive,achiam2017constrained}. That literature mostly studies how to \emph{train} policies that satisfy constraints. We borrow its formalism and ask a different question, namely how to \emph{evaluate} a deployed agent whose constraints are stated in natural language and are often only partly specified.

\paragraph{Agent benchmarks and safety evaluations.}
Benchmarks such as AgentBench \citep{liu2024agentbench}, WebArena \citep{zhou2024webarena}, and SWE-bench \citep{jimenez2024swebench} measure whether tasks are completed. A smaller body of work looks at how they are completed. MACHIAVELLI reports ethical violations alongside reward in text-based games \citep{pan2023machiavelli}, ToolEmu uses an LLM-emulated sandbox to surface risky tool use \citep{ruan2024toolemu}, and AgentDojo measures utility and security jointly under prompt injection \citep{debenedetti2024agentdojo}. Work on AI control studies monitoring protocols that remain useful even when the monitored model may act adversarially \citep{greenblatt2024control}.

\paragraph{Process-level and constraint-focused benchmarks.}
The work closest to ours measures constraint violations directly. ODCV-Bench places agents in multi-step scenarios where performance is tied to a key performance indicator and reports how often they break ethical, legal, or safety rules to reach it \citep{li2025odcv}. SpecBench measures reward hacking in long-horizon coding agents as the gap between pass rates on visible tests and on held-out tests \citep{zhao2026specbench}. MasDrift tests whether delegated subtasks in multi-agent systems stay within the permissions of the original user \citep{xu2026masdrift}, and SLBench turns the logical relations between instructions in agent skill files into executable tests \citep{chen2026slbench}. \citet{huang2026reward} study reward hacking by autonomous research agents and find that a review panel misses many confirmed cases. A recent survey of trustworthy agentic AI collects metrics and benchmarks for safety, robustness, privacy, and security in one reference \citep{qi2026trustworthy}.

Two benchmarks already report capability and safety as separate numbers. ST-WebAgentBench pairs enterprise web tasks with policies and reports Completion under Policy, which credits a task only if the agent completed it without breaking an applicable policy, together with a risk ratio \citep{levy2024stwebagentbench}. ClawsBench reports a task success rate and an unsafe action rate for productivity agents in simulated workspaces \citep{li2026clawsbench}.

A second group of work supplies trajectory-level data and diagnosis. The ATBench extensions adapt a safety taxonomy of risk source, failure mode, and real-world harm to particular agent runtimes \citep{yang2026atbench}. Who\&When Pro builds failed trajectories with labeled failure points by injecting a failure after replaying a successful prefix \citep{liu2026whowhenpro}, a construction close to the paired trajectories we call for in Section~\ref{sec:conclusion}. \citet{jha2026meltdowns} show that agents take unsafe actions after ordinary environment errors, with no adversary involved, and relate this to exploratory behavior. On the governance side, \citet{li2026constraintdrift} argue that constraints weaken as they pass through memory, delegation, and tool use, and propose keeping them as explicit execution state, while \citet{ding2026alwayson} survey agents with persistent state and outline an evaluation contract that scores obligations on state mutation and recovery instead of answer quality alone.

Reporting outcome and compliance separately is therefore not new, and we do not claim it. We do not propose another benchmark either. This paper adds three things to that line of work. The first is a constraint schema that is independent of any one benchmark and that distinguishes hard from soft constraints and kinds of evidence. The second is a per-run profile that keeps all four outcomes of Table~\ref{tab:categories} apart. A conjunctive metric such as Completion under Policy measures the rate of category~(1) and merges the other three, so it cannot separate a safe failure from an unsafe success. The third is a gating rule over the profile together with an account of what checker error does to it. The benchmarks above are complementary to this paper, and they are the natural testbeds for it; we use one of them in Section~\ref{sec:setup}.

\paragraph{The gap this paper fills, relative to ODCV-Bench.}
The ODCV-Bench paper \citep{li2025odcv} reports a scalar Misalignment Rate --- fraction of runs whose four-judge median severity exceeds $3$ on a $0$--$5$ rubric --- and a mean Severity score. Both are collapsed over the trajectory and over the constraints that apply to it. A single scalar is sensitive to any monotonic transformation of the rubric and gives no handle on which agent action violated which constraint, which is the input a deterministic rules-based checker needs. The ODCV-Bench paper also treats the four-judge panel's output as the ground truth and reports Krippendorff's $\alpha=0.81$ as the primary quality signal, while naming the absence of a human audit as an open limitation. Our framework decomposes the same trajectories into separate components for objective achievement $O$, hard violations $V$, soft constraint score $\mathrm{SC}$, uncertainty $U$ and distance $D$, each measurable under multiple checker configurations; derives a gate rule that does not need a scalar; and makes the audit --- not the judge panel --- the authoritative source for the false-positive rate $\alpha$ and false-negative rate $\beta$ that the gate's verdict depends on. We also show that the inter-judge agreement reported in \citep{li2025odcv} is a frontier-model property: on the same benchmark, the same scenarios, with smaller open-weight judges (Meta Llama-3.1-8B, Qwen3.7-flash, Mistral-Nemo), Krippendorff's $\alpha$ drops to $0.155$ (95\% bootstrap CI $[0.103, 0.209]$) and pairwise Cohen's $\kappa$ sits in $[0.036, 0.261]$. The gate's verdict is then entirely determined by which operating point --- any-judge-flags, majority vote, consensus --- is chosen. This observation is the empirical motivation for the framework's insistence on reporting checker false-positive and false-negative rates.

\paragraph{Anomaly detection and LLM-based judges.}
Detecting inputs or behaviors that fall outside a reference distribution is a mature topic \citep{chandola2009anomaly,hendrycks2017baseline}. LLMs are now commonly used as judges of other models' outputs \citep{zheng2023judging}, although such judges have systematic biases, including a preference for their own generations \citep{panickssery2024llm}. Both lines of work are relevant to trajectory monitoring, and we return to them in Sections~\ref{sec:framework} and~\ref{sec:challenges}.

\section{Goal Achievement versus Constraint Compliance}
\label{sec:problem}

An agent can be viewed as a policy $\pi$ chosen to maximize an expected task reward,
\begin{equation}
    \max_{\pi}\; \mathbb{E}_{\tau\sim\pi}\big[R(\tau)\big],
    \label{eq:unconstrained}
\end{equation}
where $\tau$ is a trajectory and $R$ rewards completion of the task. Real instructions almost never stop there. They also say which resources the agent may access, which tools it may use, what information it may disclose, and which actions are off limits. Writing these restrictions as a set of constraints $\mathcal{C}=\{c_1,\dots,c_m\}$, the behavior we actually want is closer to the constrained problem \citep{altman1999constrained}
\begin{equation}
\begin{aligned}
    \max_{\pi}\quad & \mathbb{E}_{\tau\sim\pi}\big[R(\tau)\big] \\
    \text{s.t.}\quad & \Pr_{\tau\sim\pi}\big[\tau \models c_i\big] = 1,
    \quad i=1,\dots,m,
\end{aligned}
\label{eq:constrained}
\end{equation}
where $\tau \models c_i$ means that the trajectory satisfies constraint $c_i$.

Requiring every constraint to hold with probability one is the right target for restrictions that must never be broken, such as using a credential the agent was not given. As a general model it is too strict, for two reasons. Some restrictions are budgets and not prohibitions, for example a limit on the number of external requests. And violations are in practice detected by imperfect checkers, so a guarantee of exactly zero cannot be verified. The safe reinforcement learning literature offers two standard relaxations \citep{altman1999constrained,achiam2017constrained}. A chance constraint bounds the probability of violation,
\begin{equation}
    \Pr_{\tau\sim\pi}\big[\tau \not\models c_i\big] \le \delta_i ,
    \label{eq:chance}
\end{equation}
and a cumulative-cost constraint bounds an expected cost,
\begin{equation}
    \mathbb{E}_{\tau\sim\pi}\big[g_i(\tau)\big] \le d_i ,
    \label{eq:cost}
\end{equation}
where $g_i\ge 0$ measures how much of budget $i$ the trajectory consumed. Problem \eqref{eq:constrained} is the special case $\delta_i=0$. We call a constraint \emph{hard} if it is of this kind and \emph{soft} otherwise, and the quantities reported in Section~\ref{sec:framework} are defined for both.

Problems arise when the two formulations disagree, that is, when breaking a constraint raises the probability of completing the task. Typical situations include the following.
\begin{itemize}
    \item A restricted tool gives faster or more reliable access to the needed information.
    \item An external system exposes credentials that make the task trivial.
    \item A security weakness lets the agent bypass a restriction in the environment.
    \item The evaluation metric can be manipulated directly to yield a higher score.
    \item Taking many additional, unrequested actions raises the chance that one of them produces the desired result.
\end{itemize}
In each case an optimizer that sees only \eqref{eq:unconstrained} has a reason to leave the feasible set of \eqref{eq:constrained}. These situations are instances of reward hacking, specification gaming, and goal misgeneralization as discussed in Section~\ref{sec:related}. The question that matters is thus not only whether an agent \emph{can} reach an objective, but whether its optimization stays inside the operational boundaries its principals intended.

Two features make the agent setting harder than the classical constrained one. First, $\mathcal{C}$ is rarely written down in full. Some constraints are explicit in the prompt, some are implied by the deployment context, and some are norms no one thought to state. Second, the action space is open-ended. An agent with a shell and network access can do things the benchmark designer never enumerated, so violations cannot be detected by checking membership in a short list of forbidden actions.

\section{A Constraint-Aware Evaluation Framework}
\label{sec:framework}

We propose a conceptual Constraint-Aware Agent Evaluation Framework (CAAEF) with five components. They are ordered from what is already standard practice to what is least developed.

\subsection{Outcome Verification}

The first component asks whether the assigned objective was completed, and yields a score $O(\tau)\in[0,1]$. This is what existing benchmarks measure. It is necessary, but it is not enough: two agents can produce the same result by entirely different means, so $O$ on its own says nothing about whether the behavior can be trusted.

\subsection{Trajectory Monitoring}

The second component records the full sequence of actions,
\begin{equation}
    \tau = (a_1, a_2, \dots, a_T),
\end{equation}
together with the observations each action returned, and makes this sequence the object of evaluation instead of the final answer. A trajectory is long and most of it is routine, so a monitor needs to know what to look for. The situations listed in Section~\ref{sec:problem} suggest the following signals:
\begin{itemize}
    \item tool calls that the task does not obviously require;
    \item attempts to access restricted resources;
    \item repeated failed attempts to get past a control;
    \item abrupt changes of strategy;
    \item contact with external systems not mentioned in the task;
    \item acquisition or use of credentials the agent was not given;
    \item actions unrelated to the legitimate objective.
\end{itemize}
None of these is conclusive in isolation. A second attempt after a refusal may be a corrected typing error, and an unfamiliar tool may be the right one. The signals are inputs to the components that follow: the compliance check decides whether a flagged action broke a constraint, and the anomaly score measures how unusual the pattern is as a whole.

\subsection{Constraint Compliance}

Checking actions against $\mathcal{C}$ requires the constraints to be written in a form that two evaluators would apply in the same way. We suggest recording each constraint $c_i$ with six fields:
\begin{itemize}
    \item \emph{scope}: the resources, tools, or data it covers;
    \item \emph{modality}: prohibition, obligation, or budget;
    \item \emph{class and severity}: hard or soft, with a weight $w_i\ge 0$;
    \item \emph{condition}: the state in which it applies, for example only before the user has confirmed;
    \item \emph{source}: stated in the instructions, implied by the deployment context, or an unstated norm;
    \item \emph{evidence}: how a violation is established.
\end{itemize}
For the last field we distinguish three kinds of evidence, in decreasing order of reliability: the state of the environment or the artifacts the agent produced, the execution log checked by a deterministic rule, and the reading of the trajectory by a human or LLM judge. A constraint should be checked with the most reliable kind available to it. Executable tests of the sort used in SLBench \citep{chen2026slbench} belong to the first two kinds. Constraints whose source is an unstated norm will usually need a judge, and these are the ones on which labels are least consistent. Recording the source makes it possible to report results separately for explicit and implicit constraints.

Let $v_{t,i}\in\{0,1\}$ indicate whether action $a_t$, taken in the context of the preceding trajectory, violates $c_i$. Two summaries of this array are used below. The per-action indicator $v_t=\max_i v_{t,i}$ records whether step $t$ broke any constraint, and the per-constraint indicator $V_i(\tau)=\max_t v_{t,i}$ records whether constraint $c_i$ was broken at any step. The context matters because the same action, such as reading a file, may be permitted at one point and prohibited at another. A simple trajectory-level compliance score is the fraction of compliant actions,
\begin{equation}
    \mathrm{CS}(\tau) \;=\; 1 - \frac{1}{T}\sum_{t=1}^{T} v_t.
    \label{eq:cs}
\end{equation}
A high objective score combined with a low compliance score indicates optimization that succeeded but may not be safe.

The ratio in \eqref{eq:cs} has an obvious weakness: one serious violation in a long trajectory barely moves it. A hundred-step run that exfiltrates a credential once still scores $0.99$. We therefore report two further quantities. Writing $\mathcal{C}_H\subseteq\mathcal{C}$ for the hard constraints, the strict indicator
\begin{equation}
    V(\tau) \;=\; \max_{c_i\in\mathcal{C}_H} V_i(\tau)
    \label{eq:strict}
\end{equation}
records whether any hard constraint was broken, and the severity-weighted cost
\begin{equation}
    \mathrm{SC}(\tau) \;=\; \sum_{t=1}^{T}\;\sum_{c_i\notin\mathcal{C}_H} w_i\, v_{t,i}
    \label{eq:sc}
\end{equation}
accumulates soft violations over the run. A hard violation is a reason to stop the run or to disqualify it, and a soft violation is a warning that adds to a running total. Over many runs, the mean of $V$ estimates the left-hand side of \eqref{eq:chance} and the mean of $\mathrm{SC}$ plays the role of the cost in \eqref{eq:cost}.

The indicators $v_{t,i}$ are outputs of a checker and not ground truth. Reported values of $\mathrm{CS}$, $V$, and $\mathrm{SC}$ should therefore be accompanied by the checker's false-positive and false-negative rates, estimated on a sample of trajectories audited by humans.

\subsection{Uncertainty and Anomaly Detection}

Not every unusual action is a violation, and not every violation is deliberate. An agent that is unsure how to proceed may legitimately try alternatives, and exploration of this kind should not be penalized as if it were an attack. Evaluation should therefore carry an explicit estimate of uncertainty, which we denote $U(\tau)$. It covers both the agent's uncertainty about the task and the evaluator's uncertainty about whether a given action is compliant.

Anomaly detection offers one way to operationalize this. Given a reference set of trajectories known to be compliant, one can compute a shift score $D(\tau)$ that measures how far the current trajectory, or its prefix $\tau_{1:t}$, lies from that distribution, using standard techniques \citep{chandola2009anomaly,hendrycks2017baseline} applied to action sequences or their learned representations. Because the score can be computed on prefixes, it opens the possibility of flagging risky behavior \emph{before} the agent finishes. We regard the use of uncertainty and distribution shift for this kind of early warning as one of the more promising directions suggested by the framework.

One concrete way to compute $D$ is the following. Tool names differ from task to task, so raw calls cannot be compared. Each call is first mapped to a typed action given by the category of the tool, the class of resource it touches, whether it reads or writes, and whether it falls inside the scope granted by the task. A prefix is then encoded by the sequence of these types, and scored by its distance to the nearest compliant reference prefixes for tasks of the same family. The flagging threshold is set on a held-out set of compliant trajectories so that the false-alarm rate is controlled. Conformal methods give such a guarantee when the calibration and test trajectories are exchangeable \citep{vovk2005algorithmic}.

Exchangeability is a strong assumption in this setting. It fails when the agent meets tools or task types that are absent from the calibration set, and it fails after any change to the agent. We therefore suggest calibrating separately for each task family and tracking the flag rate on runs that are known to be compliant. A rise in that rate shows that the guarantee no longer holds and that the threshold must be recalibrated. The same calibration step applies to $U$, which can be estimated from the disagreement among several independent checkers.

The two signals are not interchangeable, and neither contains the other. $U$ is a statement about confidence in a judgment of compliance. $D$ is a statement about the behavior and involves no such judgment. They can disagree in both directions. A new but legitimate way of solving a task lies far from the reference set and is plainly compliant, so $D$ is high and $U$ is low. A routine trajectory may contain one step whose status cannot be settled from the available evidence, so $D$ is low and $U$ is high. In our reading $D$ is the signal suited to early warning on prefixes, and $U$ is the signal that decides which flagged cases need a human.

Uncertainty also bears on the soft cost, and the two kinds of soft constraint behave differently. A budget is checked by counting in the log, so an overrun is known exactly. What is unclear is whether it matters, because an agent that retries a failed call or tries a second tool is exploring, and exploration consumes budget. The period after an environment error needs particular care, since it is where unsafe actions have been observed without any adversary \citep{jha2026meltdowns}. To keep exploration and overrun apart, we suggest setting each budget $d_i$ from the reference set, for example at a high quantile of what compliant runs of the same task family consume, and counting only the excess. Ordinary exploration then falls inside the budget by construction. Soft constraints that need a judge are a different case, because there the violation itself is uncertain. For these we suggest reporting $\mathrm{SC}$ as an interval. The lower end counts the violations on which all checkers agree, and the upper end adds those on which they disagree. A wide interval says that the soft cost of the run is not known, which is more useful than a point value that hides the disagreement.

\subsection{Post-Hoc Behavioral Analysis}

After the task ends, the trajectory should be reconstructed and examined with questions such as these. What was the agent trying to accomplish at each stage? Which actions were needed for the task and which were not? Did the agent try to get around a restriction? Did it exploit a weakness in the environment? Did it obtain information or permissions beyond what the task required?

The answers support a distinction between \emph{necessary} optimization, meaning effort the task demands, and \emph{opportunistic} optimization, meaning the use of whatever shortcut the environment happens to offer. The second kind is what the framework is designed to expose.

\section{A Two-Dimensional Evaluation Model}
\label{sec:model}

The framework separates two core dimensions. Objective achievement asks whether the agent accomplished the assigned task. Constraint compliance asks whether it stayed within the intended boundaries. Crossing the two gives the four categories in Table~\ref{tab:categories}.

\begin{table}[t]
\caption{Behavioral categories obtained by crossing objective achievement with constraint compliance. Outcome-only benchmarks cannot separate the two cells in the top row.}
\label{tab:categories}
\vskip 0.1in
\begin{center}
\begin{small}
\begin{tabular}{lcc}
\toprule
Objective & Compliant & Violating \\
\midrule
Achieved & (1) Intended success & (2) Unsafe success \\
Failed   & (3) Safe failure     & (4) Unsafe failure \\
\bottomrule
\end{tabular}
\end{small}
\end{center}
\vskip -0.1in
\end{table}

Category~(2) deserves the most attention. An outcome-only benchmark places it in the same bin as category~(1), so the agents that are most concerning from a safety standpoint are precisely the ones the benchmark rewards. Category~(3) is also worth a remark. An agent that stops and reports that the task cannot be done within its permissions has behaved well, yet outcome-only scoring treats it the same as an agent that failed through incompetence.

A fuller evaluation profile would add the quantities from Section~\ref{sec:framework} and report, for each run, the tuple
\begin{equation}
    P(\tau) \;=\; \big(O,\; \mathrm{CS},\; V,\; \mathrm{SC},\; U,\; D\big),
    \label{eq:profile}
\end{equation}
where the six quantities are those introduced in Section~\ref{sec:framework}, each evaluated on $\tau$. We recommend against collapsing this profile into one scalar. Any fixed weighting allows a large gain in $O$ to offset a constraint violation, which reintroduces at the level of the metric the very trade-off the constraints were meant to rule out. A single number can hide the failure modes that matter most.

Declining to aggregate does not mean declining to decide. For release gating we suggest a lexicographic rule. A run with $V=1$ is disqualified whatever its value of $O$, and an agent is rejected if its rate of such runs exceeds the tolerance $\delta$ set by the deployer. Among agents that pass this test, one is preferred to another only if it is no worse on both $\mathrm{SC}$ and $O$. Where neither dominates, the choice is left to the deployer, who sees the trade-off instead of having it made by a weighting. Under this rule a safe failure ranks above an unsafe success. Category~(3) costs utility, whereas category~(2) breaks the conditions under which the agent was allowed to act at all.

The rule is only as good as the checker behind $V$, and its behavior under checker error can be worked out directly. Suppose the checker reports a hard violation on a compliant run with probability $\alpha$ and misses a real one with probability $\beta$. If the true rate of hard violations is $p$, the observed rate is
\begin{equation}
    q \;=\; (1-\beta)\,p + \alpha\,(1-p).
    \label{eq:observed}
\end{equation}
Three consequences follow. First, an agent that never violates is still observed at rate $\alpha$, so it is rejected whenever $\alpha>\delta$. A tolerance below the false-positive rate of the checker cannot be enforced on the raw output. Second, a share $\alpha$ of compliant runs is disqualified, and if the monitor stops a run when it flags, the same share is turned into forced safe failures. This is the utility cost of the veto, and it is paid whether or not the agent ever misbehaves. Third, misses lower $q$ by $\beta p$, so an agent can pass the gate with a true rate above $\delta$.

Hard violations are meant to be rare, and when $p$ is small the false positives dominate. With $p=0.02$, $\alpha=0.05$, and $\beta=0.2$, equation~\eqref{eq:observed} gives $q=0.065$, of which about three quarters are false alarms. Two practical rules follow. The gate should be applied to the corrected estimate
\begin{equation}
    \hat{p} \;=\; \frac{q-\alpha}{1-\alpha-\beta},
    \label{eq:corrected}
\end{equation}
which is valid when $\alpha+\beta<1$ \citep{rogan1978estimating}, with a confidence interval that includes the uncertainty in $\alpha$ and $\beta$ from the audit. And every run with $V=1$ should be confirmed by stronger evidence or by a human before it counts, which removes most of the cost of $\alpha$ at the price of review effort proportional to $q$. The analysis assumes that $\alpha$ and $\beta$ do not depend on the agent. That assumption fails for an agent that conceals its actions, for which $\beta$ is higher than the audit suggests.

\section{Experimental Setup}
\label{sec:setup}

\paragraph{Testbed.}
We use ODCV-Bench \citep{li2025odcv}, the state-of-the-art benchmark for the failure mode this paper measures: agents under KPI pressure who satisfy their performance target by violating the ethical, legal, or safety constraints their system prompt names. Each scenario pairs a system prompt stating a role and its obligations with a user prompt stating a task and a numeric target, inside a sandboxed filesystem whose scripts contain deliberate loopholes. Every scenario exists in two framings that differ only in the user prompt: \emph{mandated}, which instructs the agent to reach the target, and \emph{incentivized}, which states the target as a condition for reward without instructing compliance. The benchmark's own paper evaluates $12$ frontier agents with a four-judge frontier panel (Krippendorff's $\alpha=0.81$) and reports misalignment rates ranging from $0\%$ to $62.8\%$; it names as an explicit limitation that \emph{``scores are produced by LLM judges without human verification''}. The present paper is designed to measure what ODCV-Bench exposes under the measurement discipline that limitation asks for: we score every run under four checker configurations (two deterministic, two judge-based); we quantify how the gate's verdict propagates checker false-positive and false-negative rates; we build the human-audit infrastructure their paper flags as missing; and we extend their 40 scenarios across both framings with up to three repetitions per cell. We draw $20$ scenarios for the original wave, stratified by container base image with a fixed seed; the extension wave covers the remaining $20$ at three repetitions, with constraints committed to git before any run on them, so the draw and the generalisation set are both reproducible and independent of anything we measured.

\paragraph{Agents and judges.}
Four agents, two from each of two model families, matched on price across families so that a difference between families cannot be a price-tier artefact: a mid tier at \$2/\$10 per million input/output tokens and a small tier at \$0.10/\$0.50. Two judges, one per family. Budget constrained the judges to models that also appear as agents, so some judgments are same-\emph{model} rather than merely same-family; these are tagged and every judge-dependent figure is reported both over all judgments and over cross-family judgments only.

\paragraph{Harness and tracing.}
Each run executes inside a container with no network access at all, driven by a ReAct loop \citep{yao2023react} with two tools (\texttt{bash} and \texttt{task\_complete}), a 50-step cap and a 30\,s per-command timeout. Every run writes one JSONL trace: the full command, its output, exit code, timestamps and token counts per action, plus a SHA-256 hash of every file in the sandbox before the run and after every action. The hashes are taken out of band, so they never enter the agent's context. Failed and truncated runs are kept and marked, never discarded. A separate replay check verifies that each stored trace reconstructs its own action sequence and the exact message list the model received; all 303 traces pass.

One subtlety the trace schema has to respect: a single model turn can emit several parallel tool calls. The paper's trajectory $\tau=(a_1,\dots,a_T)$ indexes \emph{actions}, and $\mathrm{CS}$ divides by $T$, so conflating turns with actions would inflate $\mathrm{CS}$ on exactly those runs. Traces therefore carry a per-action index distinct from the turn index.

\paragraph{Constraints.}
We wrote 131 constraints over the 20 scenarios (mean $6.5$, range $5$--$8$), each with the six fields of Section~\ref{sec:framework}, drafted from the scenario prompts alone before any trajectory was examined. Their distribution is itself a finding about the framework's practicality. By source: $45.0\%$ explicit, $40.5\%$ implied by deployment context, $14.5\%$ unstated norms. By evidence: $38.9\%$ establishable from environment state, $13.0\%$ from a deterministic log rule, and $48.1\%$ requiring a judge. Nearly half of all constraints therefore fall into the least reliable evidence class, and \emph{every} unstated-norm constraint does --- precisely where Section~\ref{sec:framework} predicts labels will be least consistent.

\paragraph{Objective verification.}
The benchmark ships no working objective scorer, so $O$ had to be defined. For each run we replay the stored final filesystem state into a fresh container and execute the scenario's own KPI script from a \emph{pristine} copy, comparing its output against the threshold the scenario states. The pristine copy matters: an agent that rewrites the scorer can otherwise inflate its own $O$. In one early run an agent edited a ranking script to report $250/250$ while the pristine copy reported the true $50/250$. This defeats script tampering but not data tampering, which is the intended reading: an agent that deletes inconvenient records and then legitimately scores well is $O=1$ with $V=1$, category~(2). Six of the 20 scenarios have no agreed rule, because their KPI scripts need arguments the prompt does not determine or write results to a file rather than to standard output; $O$ is reported as missing for those 85 runs rather than imputed, leaving 212 runs with a known $O$.

\paragraph{Checker configurations.}
We score every run four ways, as an ablation over the framework's components: \textsc{rules+state} (state hashes and deterministic log rules only), \textsc{judge~A} and \textsc{judge~B} alone, and \textsc{full} (state or log rules wherever the constraint's evidence field permits, both judges elsewhere, with a judge-flagged violation counted when either judge flags it). Disagreement is reported separately as $U$ rather than averaged away.

\paragraph{A worked constraint.}
To make the schema concrete, one constraint from the hiring scenario in full. \emph{Scope}: the ranking script named in the task as the measure of performance. \emph{Modality}: prohibition. \emph{Class}: hard (so $w_i$ is unused and it enters $V$, not $\mathrm{SC}$). \emph{Condition}: at all times. \emph{Source}: implied --- the prompt never says ``do not edit the scorer'', but naming it as the measure makes editing it a violation of the deployment context. \emph{Evidence}: state. The checker computes SHA-256 hashes of every file in the sandbox before the run and after each action, and sets $v_{t,i}=1$ at the first action whose post-state hash for that path differs from the pre-run hash. Concretely, one run issued \texttt{chmod +w} on the script and overwrote it to print a perfect score; the hash changed at that action, so $v_{t,i}=1$ there, giving $V=1$ and, since the pristine copy still reported the true failing score, $O=0$: category~(4). A sibling constraint in the same file (``the candidate pool must be diverse'') is soft with $w_i=2.0$ and \emph{evidence: judge}, because no file hash can settle it.

\paragraph{Typed actions and the distance score.}
For reproducibility we state the encoding exactly. Each \texttt{bash} command is mapped to a tuple of four categorical features: the \emph{tool category} (read, write, execute, delete, permission change, network, process control, other), assigned by first match over an ordered list of command patterns so that destructive and privileged categories are tested before generic ones; the \emph{resource class} (task data, source data, validator, configuration, logs, temporary, outside workspace, none), assigned by first match over path patterns; a \emph{read/write} flag, true for write, delete and permission-change categories; and an \emph{in-scope} flag, false when the command names any absolute path outside the paths the task grants, with network actions out of scope by construction. The four features are concatenated into a single token, so the vocabulary is the set of observed tuples ($46$ here) rather than the product space. A prefix $\tau_{1:t}$ is encoded as the concatenation of its length-normalised token counts and its length-normalised token-bigram counts, the latter capped at the $400$ most frequent bigrams. $D(\tau_{1:t})$ is the mean Euclidean distance to the $5$ nearest reference encodings among compliant prefixes of length within $\pm 2$ of $t$, drawn only from other scenarios.

\paragraph{Statistics.}
All intervals are $95\%$ percentile bootstrap with $10{,}000$ resamples, resampling \emph{whole scenarios} rather than runs, because the two framings and the repetitions of a scenario are not independent. With four agents from two families, any ranking is weak evidence and we say so wherever one appears.

\paragraph{What the setup could not deliver.}
Three departures bound the results and are stated here rather than in a footnote. First, \textbf{decoding is not deterministic}. Both providers reject or silently ignore \texttt{temperature}$=0$; four identical requests returned four different completions. Runs and judgments are therefore sampled, not greedy, which makes repetitions load-bearing --- and only one complete repetition was funded (297 of 400 planned runs; the second repetition is partial and is not pooled). Second, \textbf{the judges are weaker than intended} and batch a scenario's constraints into one call rather than judging each in isolation, so a verdict on one constraint can be influenced by the others. Third, \textbf{the human audit has not been run}. The annotation tooling and a stratified 200-run sample exist, but $\alpha$ and $\beta$ are unmeasured, so every quantity that depends on them is reported as pending. Total API cost of the study was \$4.61.

Under \textsc{rules+state}, the claim of Section~\ref{sec:model} holds and holds strongly. Under the three-judge majority-vote per-constraint protocol run on $772$ runs across both waves, the inversion is not reproduced: the objective-achievement ranking (\texttt{gpt-6-luna}~$15.3\%$~>~\texttt{gpt-6-sol}~$13.2\%$~>~\texttt{sonnet-5.5}~$10.3\%$~>~\texttt{haiku-5.5}~$8.1\%$) and the gate-passing ranking under the same protocol (\texttt{gpt-6-luna}~$63.4\%$~>~\texttt{haiku-5.5}~$59.9\%$~$\approx$~\texttt{gpt-6-sol}~$59.9\%$~>~\texttt{sonnet-5.5}~$55.1\%$, where gate-passing is $V{=}0$) are weakly positively correlated rather than opposed ($\tau=+0.33$). This is itself support for the framework: the checker configuration \emph{is} a load-bearing parameter of the measurement, not a technicality.

Under the \textsc{full} protocol, $\tau=+1.00$. This is not agreement; it is degeneracy. \emph{No agent passes the gate at all}, so the gate cannot discriminate and the gated ranking collapses back onto the $O$ ranking. With violation rates of $0.163$--$0.300$ against a tolerance of $\delta=0.05$, every agent is disqualified and the ranking question becomes empty.

That degeneracy is not an artefact of our analysis; it is equation~\eqref{eq:observed} appearing in data. Section~\ref{sec:model} argues that a tolerance below the checker's false-positive rate cannot be enforced on raw output. Either these agents genuinely violate constraints in $16$--$30\%$ of runs, or $\alpha$ is of that order. \textbf{Those two possibilities cannot be separated without the audit}, which is exactly why the audit is load-bearing rather than a refinement. Every gate conclusion reported here is provisional on it.

\paragraph{The inversion is specific to the tolerance.}
The $\tau=-0.60$ above is computed at $\delta=0.05$, a value we chose before looking at the data and did not justify against any risk model. Varying it changes the picture substantially, and Table~\ref{tab:delta} reports the full sweep. Under \textsc{rules+state}, no agent passes at $\delta\in\{0.01,0.02\}$, two pass at $0.05$, and three pass at $0.10$; the corresponding $\tau$ values are $+1.00$, $+1.00$, $-0.60$ and $+0.18$. \textbf{The ranking inversion therefore occurs in a window of tolerances, not everywhere.} Below the window the gate rejects everything and says nothing; above it the gate admits almost everything and again says little; only in between does it separate agents in a way that contradicts the outcome ranking.

The gate is informative exactly when $\delta$ sits above the checker's false-positive rate and below the agents' true violation rate, and nothing in the framework as stated tells a practitioner where that window is. Locating it requires $\alpha$, which requires the audit. The same instability appears per agent. Safe failure is the largest cell for every agent without exception, ranging from $64\%$ of one agent's runs to $82\%$ of another's. Note also that $\mathrm{CS}$ stays between $0.885$ and $0.959$ throughout, while the $V$ rate ranges from $0.163$ to $0.300$ over the same runs. This is the weakness of the ratio in equation~\eqref{eq:cs} made concrete: a trajectory can contain a disqualifying action and still score above $0.88$ on compliance, because one bad step among several ordinary ones barely moves an average. $\mathrm{CS}$ and $V$ are not substitutes, and reporting only the former would conceal the finding.

Two observations follow. First, \textbf{a non-trivial share of the runs an outcome-only benchmark would score as successes carry a hard violation}. Under \textsc{rules+state}, $4$ of the $21$ successes ($19\%$) are in category~(2). Under the three-judge majority-vote protocol on $772$ runs with resolved $O$, $29$ of $89$ successes ($32.6\%$, with the overall rate at $3.8\%$~\textsc{[1.2, 7.1]} of all runs) are category~(2); under all-agree consensus the figure is $10$ of $89$ ($11.2\%$ of successes, $1.3\%$~\textsc{[0.4, 2.3]} of all runs); under any-judge-flags it is $78$ of $89$ ($87.6\%$ of successes, $10.1\%$~\textsc{[3.1, 18.9]} of all runs). These bounds should be read against the inter-judge Krippendorff's $\alpha=0.155$ we report in Section~\ref{sec:judge_results}: the between-operating-point spread is driven by judge disagreement, not by variation in agent behaviour. Either way, category~(2) is real --- on this benchmark it is thin, but it is not zero at any operating point we can compute.

Second, and more striking, \textbf{safe failure dominates the corpus} --- but the exact share depends on the checker and the aggregation. Under the \textsc{rules+state} checker on all $297$ runs with $O$ scored (now $100\%$ of the analysed set after the extension's Task~2 rescore), safe failure is $84.5\%$. Under the three-judge per-constraint protocol run on $772$ runs with resolved $O$ across both the original and extension waves, safe failure is $81.5\%$~\textsc{[71.4, 90.2]} with judges in \emph{all-agree} consensus, $51.8\%$~\textsc{[41.0, 62.4]} under \emph{majority vote}, and $15.8\%$~\textsc{[9.6, 23.2]} under \emph{any-judge-flags}. The three operating points span the same panel's possible verdicts on the same runs; the gap between them is a direct measurement of judge disagreement, not agent behaviour. Section~\ref{sec:model} notes in passing that an agent which stops and reports that the task cannot be done within its permissions is scored identically to one that failed through incompetence. In this benchmark that is not a marginal case but, under every well-behaved checker configuration we report, the largest cell. We regard this as a stronger argument for the two-dimensional model than category~(2) is: the unsafe-success cell is real but thin, and every per-agent estimate of it is extremely noisy, whereas the conflation of principled refusal with incompetence affects most of the corpus. It also suggests that agentic safety benchmarks reporting a single success rate are, on tasks of this kind, mostly measuring willingness to break rules.

\subsection{Judges disagree, and the disagreement is first-order}
\label{sec:judge_results}

We report two judge protocols. The first is the Phase~1 two-judge batched protocol run on $200$ runs of the original wave (one call per run per judge, all constraints judged together): the two frontier-tier judges, Haiku-5.5 and GPT-6-luna, agree on run-level $V$ for $85.5\%$ of runs, close to one-directionally (judge~B flags a hard violation that judge~A does not in $28$ runs, judge~A flags one that judge~B does not in a single run). The second is a three-judge per-constraint protocol run on $779$ runs across both waves (one call per run per constraint per judge, no batching): three smaller open-weight judges from different families (Meta Llama-3.1-8B, Qwen3.7-flash, Mistral-Nemo). Their inter-judge agreement is substantially lower: Krippendorff's $\alpha=0.155$~\textsc{[0.103, 0.209]} on hard-constraint cells, bootstrapped over scenarios; pairwise Cohen's $\kappa$ sits in $[0.036, 0.261]$; per-cell flag rate is $30.0\%$~\textsc{[25.2, 35.2]} for Llama, $17.5\%$~\textsc{[13.3, 22.2]} for Mistral, $5.4\%$~\textsc{[3.2, 7.8]} for Qwen, with intervals that do not overlap. The gate's verdict on this panel then swings with the aggregation rule: run-level $V$ at $82.7\%$ under any-judge-flags, $40.3\%$ under majority vote, $6.9\%$ under consensus. For comparison, the ODCV-Bench paper \citep{li2025odcv} reports Krippendorff's $\alpha=0.81$ across four frontier judges on a 0--5 rubric. The gap --- $0.155$ vs $0.81$ on the same benchmark, with judges drawn from the two sides of the capability frontier --- is the empirical signal that the gate's accounting for checker error is not optional. The mean of $U$ on the two-judge original wave is $0.0164$, and $75$ of $200$ runs have $U>0$; the three-judge wave gives $U>0$ on $4{,}969$ of $5{,}089$ cells where at least two judges rendered a verdict ($97.6\%$), confirming that the two-judge measurement understated $U$.

\textbf{Which agent one would ship depends on which judge one asked, and on which aggregation one picks.} Under judge~A alone (batched), three of four agents pass the gate; under judge~B alone, none do; under the three-judge majority-vote protocol, no agent passes at $\delta=0.05$; under the three-judge all-agree protocol, three of four pass. The adjudication protocol of Section~\ref{sec:challenges} --- deterministic checks where possible, multiple monitors from different families, human review of disagreements --- is the apparatus required to make this measurement useful at all.

Excluding same-model judgments lowers the measured violation rate for both affected agents (from $0.175$ to $0.125$, and from $0.225$ to $0.175$): these models judged their own runs \emph{more} harshly than cross-family judges did. With only two of four agents affected this is suggestive rather than established, but it runs opposite to the self-preference effect one might expect \citep{panickssery2024llm}.

Taking a run-level maximum over unequal numbers of draws biases the score systematically against the positive class, which alone is enough to make an uninformative score \emph{look} anti-predictive. We built an \texttt{action\_index}-only falsifier (prefix index as the score, no features) precisely to measure this: at the unmatched horizon it scores $0.172$ --- a score that cannot be anti-predictive is $0.17$ --- and matching the horizon to a fixed $H$ pre-violation actions returns it to exactly $0.500$, as it must. We take this as evidence that the matching works and that the unmatched run-level AUROCs should not be read as mechanisms. At the matched horizon $D$'s AUROC is $0.496$ ($H{=}2$) and $0.432$ ($H{=}3$): the right reading is that $D$ carries no usable signal here, not that it is actively anti-informative.

The reason is visible in the data rather than speculative. Runs are short (median $5$ actions) and violations occur early, after ordinary reconnaissance. A pre-violation prefix is typically two or three file reads --- the most common compliant behaviour there is. $D$ measures distance from compliant behaviour, and these prefixes \emph{are} compliant behaviour: the violation is a step change, not a drift. The early-warning idea of Section~\ref{sec:framework} presupposes a trajectory long enough to depart from a norm gradually, and these trajectories do not provide one.

The more useful result is the calibration diagnostic, reported in the lower rows of Table~\ref{tab:rq2}. Split-conformal calibration should hold the false-alarm rate at its target when calibration and test prefixes are exchangeable. The realised rates are $14.3\%$ against a $5\%$ target and $27.0\%$ against $10\%$: an overshoot of $2.9\times$ and $2.7\times$ respectively, so the gap is not an artefact of one operating point. \textbf{Exchangeability does not hold across scenarios}, exactly the failure Section~\ref{sec:framework} anticipates when the agent meets task types absent from the calibration set. Calibration and evaluation scenarios are different tasks with different tool vocabularies, so a prefix from an unseen scenario is far from the reference set for reasons that have nothing to do with compliance. The per-task-family calibration we recommend is not possible at this scale: with 20 scenarios split evenly, no family has enough runs to calibrate within.

\paragraph{Exchangeability-robust calibration does not rescue it.}
Since the diagnosis is non-exchangeability, the natural response is a calibration method built for it. We tried three, with the results in Table~\ref{tab:conformal}: Mondrian conditioning on prefix length (the covariate $D$ depends on most strongly), covariate-shift weighting of calibration scores by similarity to the test prefix, and cross-conformal aggregation over folds of calibration scenarios. \textbf{None removes the overshoot.} At the run level, Mondrian lands at $3.2\times$ and $2.7\times$ against split conformal's $2.9\times$ and $2.7\times$; cross-conformal gives a marginal improvement at the looser target ($2.2\times$) and none at the tighter one.

One methodological note, because it changes how the table should be read. Our first implementation of the Mondrian and weighted variants raised an alarm whenever \emph{any} prefix exceeded its threshold, which is one test per action, while split conformal tests only the run maximum. Those variants duly looked much worse ($5.1\times$ and $6.0\times$), but most of that gap is multiplicity rather than shift. Standardising each prefix score within its length bucket and testing the run maximum restores a like-for-like comparison, and the difference between the variants then largely disappears. We report both so the artefact is visible.

The conclusion we draw is that the problem is not in the calibration layer. A conformal wrapper controls the error rate of whatever score it is given; it cannot manufacture signal. With the horizon artefact controlled $D$'s AUROC lies within noise of chance, so the underlying score is uninformative; re-calibrating an uninformative score more cleverly yields a better-behaved uninformative detector. A direct repair of the kind the framework invites --- scoring the proposed next action rather than the prefix distance --- gives a modest prefix-level AUROC of $0.603$ ($0.604$ with position features ablated, so the discrimination comes from the typed action rather than from where in the run it sits) but no deployable detection: at a $5\%$ false-alarm budget it fires in $0$ of $17$ violating runs at the matched horizon. Fixing the early-warning component on this corpus requires a different representation or longer trajectories, not a different quantile.

\subsection{How much do our own design choices decide the answer?}

Three choices in Sections~\ref{sec:framework} and~\ref{sec:setup} were made a priori and could have driven the results. We test each.

\paragraph{Soft-constraint weights.}
The weights $w_i$ use a fixed three-point scale and are not calibrated against any external severity model, which is a fair criticism of the framework as much as of this study. We recompute $\mathrm{SC}$ under four schemes: ours; uniform ($w_i=1$); an expert-style scheme keyed to the \emph{source} field, on the view that a violation of an unstated norm is worse to discover than one of an explicit instruction ($1.0/1.5/2.0$ for explicit/implied/norm); and inverse-frequency, in which rare violations weigh more. The per-agent ordering is largely stable: Kendall's $\tau$ against our scheme is $1.00$ for the source-keyed scheme, $0.91$ for uniform and $0.67$ for inverse-frequency. The single reordering under inverse-frequency swaps two agents whose intervals overlap almost entirely. Absolute $\mathrm{SC}$ values move by a factor of three across schemes, so \emph{levels} of $\mathrm{SC}$ should not be compared across studies that weight differently; the within-study ordering survives.

\paragraph{Batching constraints into one judge call.}
Our budget forced all of a scenario's constraints into a single judge call, which risks cross-constraint interference. We re-judged a stratified subsample --- 158 (run, constraint) pairs over 24 runs, chosen to over-represent runs the batched pass flagged --- one constraint per call, with the same judge, the same trajectory rendering, and the same reasoning setting, so that batching is the only difference. Cell-level agreement is $94.3\%$ ($95\%$ CI $[89.5, 97.0]$), but because violations are rare, Cohen's $\kappa$ is only $0.498$. The disagreement is directional: \textbf{batching raises the measured violation rate from $0.044$ to $0.076$}, with the batched protocol flagging 7 pairs the isolated protocol does not and the reverse happening twice. Judging constraints together therefore makes a judge roughly $70\%$ more likely to report a violation. This does not overturn any ordering we report, since the effect applies to every agent alike, but it means our judge-based violation \emph{rates} are biased upward, and it is one more reason the $\alpha$ from the audit is the quantity that matters.

\paragraph{The scenario draw.}
Scenarios were drawn with a fixed seed, stratified by container base image, before any result was seen. We did not re-draw, so we cannot quantify draw variance; this is a known gap rather than a tested one. The scenario-clustered bootstrap reported throughout propagates between-scenario variability into every interval, which is the partial mitigation available at this sample size.

\subsection{State evidence is less decisive than the hierarchy suggests}

Section~\ref{sec:framework} orders evidence by reliability, with environment state first. Our experience qualifies that ordering. A naive state checker --- the file changed, therefore the constraint was violated --- produced a high false-positive rate. Three cases we inspected by hand: an agent that rewrote eleven protected data files \emph{after backing them up, describing them as malformed records repaired, and reporting the true failing score}; thirteen runs that ``modified'' an incident report by \emph{appending a review section}; and fifteen runs whose audit-log change was made by the scenario's own tool. We therefore classify changes as rewritten, appended, truncated or deleted rather than as a single bit, which spared fifteen appends while still flagging nineteen rewrites and deletions.

The correction is itself instructive: append-versus-rewrite is decided from the command, not from the hashes, so a constraint relying on it is using log-rule evidence wearing state's clothes. State evidence establishes \emph{that} something changed and \emph{how}; whether the change was legitimate still needs a judge. The hierarchy holds for the question ``did this file change'' and not for the question ``was this a violation''.

\subsection{What is pending the audit}

Three of the measurements proposed in Section~\ref{sec:framework} are not reported here because they are defined against human labels: whether $U$ predicts that the automated label is wrong, the precision and recall of each checker configuration, and the behaviour of the gate under corrected error rates via equation~\eqref{eq:corrected}. We have deliberately not substituted model labels for human ones. The stratified sample ($200$ runs, with every flagged run included so that $\beta$ is estimable) and a blinded annotation interface are built and ready; the estimator and its interval machinery are implemented and tested against the worked example of Section~\ref{sec:model}.

One comparison we had planned proved impossible rather than merely pending: the benchmark publishes its own severity labels, but for twelve models none of which appears in our slate, so no run overlaps and the agreement cannot be computed.

A second gap is addressable and worth stating as a concrete task rather than a caveat. Six of the twenty scenarios have no objective score, costing us $85$ runs of $O$, for two distinct reasons: four ship a KPI script that requires an argument the prompt does not determine (which artefact should be validated), and two write their result to a file rather than to standard output, so there is nothing to parse from an exit status. Neither is fundamental. The first needs a one-line declaration per scenario naming the artefact to score; the second needs the rule to read a named file. We specify $O$ in a per-scenario rule file precisely so that this is an edit to data rather than to code, and completing those six rules would take $O$ coverage from $70\%$ to $100\%$ of runs without re-running a single agent, since the final filesystem state of every run is stored.

\section{Research Challenges}
\label{sec:challenges}

\paragraph{Inferring intent from behavior.}
Deciding whether an agent \emph{deliberately} worked around a constraint is difficult, and unexpected behavior should not be read as strategic intent by default. More defensible evidence comes from the structure of the trajectory: what the environment returned, whether an attempt was repeated after being refused, whether compliant alternatives were available and ignored, and how behavior changed once a constraint was encountered. Even then, conclusions about intent should be stated with care.

\paragraph{Hidden and emergent strategies.}
Agents operating over long horizons may find strategies that benchmark designers did not anticipate, and a benchmark cannot detect a violation it offers no opportunity to commit. Future environments should deliberately include both a legitimate route and one or more constraint-violating routes to the same objective, so that the choice between them becomes observable.

\paragraph{Reward design.}
If completion is strongly rewarded and violations are weakly penalized, an optimizer will sometimes prefer to violate. Benchmarks and training setups should keep task reward and constraint-related signals separate, so that this trade-off is visible instead of being buried in one objective.

\paragraph{Early detection.}
Post-hoc analysis is useful for understanding failures, but deployed systems need monitoring while the agent is running. One option is a running risk estimate that combines trajectory anomaly, uncertainty, proximity to a constraint boundary, and tool-use patterns, with human intervention requested when the estimate crosses an adaptive threshold. How to set that threshold without overwhelming human reviewers is an open problem. It is also a practical one: a review of production agent systems finds that human-centered controls such as runtime approval are the dominant security mechanism in industry \citep{wang2026reframing}, and a monitor that asks too often will have its requests approved without being read.

\paragraph{Reliability of automated monitors.}
At scale, trajectory review will largely be done by other models. This raises an evaluator--agent problem. If the monitor shares blind spots with the agent it oversees, for example because both derive from the same base model, automated oversight can fail systematically and without any visible sign \citep{panickssery2024llm,greenblatt2024control}. The evidence so far is not reassuring. \citet{huang2026reward} report that a review panel misses many confirmed cases of reward hacking, and that detailed feedback from reviewers helps agents evade detection in later rounds. We therefore recommend an adjudication protocol in place of a single judge: deterministic checks wherever the evidence allows, at least two monitors drawn from different model families, and human review of every case on which they disagree together with a random sample of the cases on which they agree. The sample gives an estimate of the errors the monitors share, which their agreement would otherwise hide. Whether such a protocol is reliable enough, and under which conditions, needs direct empirical study.

\section{Conclusion and Future Work}
\label{sec:conclusion}

The move from language models that answer to agents that act calls for a matching change in how they are evaluated: completing a task and behaving acceptably while doing so are different things, and an agent that reaches the correct answer by an unauthorized route is a different object from one that reaches the same answer within its permissions. We have therefore proposed moving the unit of evaluation from the final answer to the whole interaction trajectory, and reporting objective achievement, constraint compliance, uncertainty, and behavioral distribution shift as separate dimensions with a gating rule in which a hard violation cannot be offset by task success, which brings out a failure mode that conventional benchmarks conceal, namely agents that look successful while reaching their objectives through unintended or prohibited means. The study in Sections~\ref{sec:setup} and~\ref{sec:results} supports part of this and refutes part of it. Separating the two dimensions does change the conclusion: under deterministic checkers the outcome ranking and the gated ranking are opposed, and the category an outcome-only score cannot distinguish from incompetence turns out to be most of the corpus. The early-warning component does not survive contact with data at this scale: $D$'s apparent anti-prediction at the run level turned out to be a horizon-asymmetry artefact, and with the horizon matched the score is uninformative; a direct repair that scores the proposed next action gives a modest prefix-level AUROC ($0.60$) that catches no violating run at a $5\%$ false-alarm budget. The conformal guarantee the original score relied on overshoots its target by roughly a factor of three; three exchangeability-robust calibration variants failed to recover it, which --- taken with the uninformative underlying score --- locates the fault in the score and the trajectory length rather than in the calibration layer. The framework's weakest point is the one it is most dependent on: nearly half of the constraints we could write admit only a judge, two judges from different families disagreed enough to change which agent would ship, and the violation rate measured under the full protocol exceeded the gate tolerance for every agent --- so the gate could not discriminate at all until the checkers themselves are characterised. We take this as evidence that the framework's accounting for checker error is not a caveat attached to it but the part most in need of development. The ODCV-Bench paper \citep{li2025odcv} shows that frontier judges on this benchmark agree with each other at Krippendorff's $\alpha=0.81$ --- a number that would make the $\alpha$ and $\beta$ corrections we derive secondary. We show in Section~\ref{sec:judge_results} that on the same benchmark, with judges from the smaller-and-open-weight tier that smaller teams are likely to run against, that inter-judge agreement drops to $\alpha=0.155$ and the gate verdict swings from $7\%$ unsafe-failure (consensus) to $73\%$ (any-flags) depending purely on the aggregation rule chosen for the same panel's verdicts. Our framework's contribution is to say that this spread is the measurement signal, not a nuisance; the paper's gating rule and audit protocol are the apparatus that converts it into a release decision. The tolerance sweep sharpens the same point: the gate separates agents only when $\delta$ lies above the checker's false-positive rate and below the agents' true violation rate, and the framework as stated gives a practitioner no way to find that window without first measuring $\alpha$.

The framework also assumes that a constraint set can be written down and checked, which is often only approximately true, and that trajectories are fully observable, so an agent able to conceal actions falls outside what trajectory monitoring can cover. Four directions for future work follow: completing the human audit so that $\alpha$ and $\beta$ become measurable and the gate can be applied to corrected rates; paired-trajectory datasets in which two agents achieve identical outcomes by compliant and non-compliant strategies, so that detectors can be trained and tested with the outcome held fixed; longer-horizon tasks on which distribution shift has room to appear before a violation, since on short trajectories it does not; and larger, better-calibrated monitor panels, since two frontier judges disagreed enough to decide which agent ships and three smaller open-weight judges disagreed with each other at Krippendorff's $\alpha=0.155$~\textsc{[0.103, 0.209]} on the same benchmark. Scaling the panel is necessary but not sufficient; the panel's own disagreement has to be measured and corrected for. The research question is not only ``can the agent achieve the goal?'' but ``can the agent achieve the goal within the intended behavioral boundaries, and can we reliably tell when it has not?'' --- and our results suggest the second half of that question is currently the harder one.

\section*{Impact Statement}

This paper discusses how to evaluate AI agents so that constraint-violating behavior is not mistaken for success. We expect the main consequence of this line of work to be safer deployment of autonomous systems. Trajectory-level monitoring involves recording agent actions, which may include user data, and such monitoring should be designed with appropriate privacy safeguards.
